# f-Itinera Planning Simulation Library

f-Itinera is a highly dynamic, functional financial planning pipeline framework designed for mathematically validating a
wide range of financial planning scenarios. The simulation is built around a unified financial data model (Persons,
Accounts, etc.) and processed by a pipeline of logical components called Flows and Metric Generators.

Some features include:

- A flexible data model centered around:
  - Accounts (which can be assets or liabilities, external or internal sources of funds)
  - Persons (whose attributes can be leveraged to determine logical states)
  - Transactions (which are the atomic units of change to Account objects)
  - Metrics (which are calculated based on the state of the simulation at each "turn".)
- A flexible simulation engine that can be extended to include any kind of user-specified calculation (e.g. tax,
  mortgage, rental income, expenses, purchasing real estate, investment modeling, etc.).
  > NOTE: The library provides a solid foundation of common financial calculations to get you started!
- A flexible result format that can be extended to include user-specified metrics.

> NOTE: f-Itinera stands for "Fiscus Itinera". While not correct latin, this roughly translates to "Fund Trips" in
> english. Our liberal interpretation of this is more like funding your wealth journey, which is at the heart of any
> finanicial plan.

## Executive Summary

f-Itinera introduces a highly dynamic, functional **financial planning pipeline** framework.

The primary goal is to maximize expressiveness by enabling custom, dynamic, user-provided logical Flows to process a
unified financial data model.

## What is Fitinera?

Fitinera is a Python library for **mathematically validating financial planning scenarios** through a programmable
simulation pipeline. It is intended for developers and financial planners who want to model complex, dynamic household
finances — retirement timing, mortgage payoff, income transitions, and more — using plain Python logic rather than rigid
configuration schemas.

## Installation

Install via `pip` or `uv` (recommended). Fitinera is built using [uv](https://github.com/astral-sh/uv) for
high-performance dependency management.

```bash
# Recommended
uv add fitinera

# Alternative
pip install fitinera
```

Import the core components to get started:

```python
from fitinera import (
    SimulationScenario,
    Person,
    Account,
    Age,
    Date,
    EngineConfiguration,
    TurnDuration,
    SimulationEngine,
    Flow,
    MetricGenerator,
    Income,
    Expense,
    Transfer,
)
```

## Quickstart API Examples

```python
# 1. Define the Data State (Scenario)
scenario = SimulationScenario(
    initial_persons=[
        Person(
            id="Sam",
            age=Age(years=34, months=2),
            expectancy=Age(years=99),
            labels={"Status": "Working"},
        ),
        Person(
            id="Alex",
            age=Age(years=33, months=8),
            expectancy=Age(years=99),
            labels={"Status": "Working"},
        ),
    ],
    initial_accounts=[
        Account(
            id="Joint Checking",
            initial_balance=10000,
            labels={"Type": "ASSET", "Liquidity": "LIQUID"},
        ),
        Account(id="Mortgage", initial_balance=300000, labels={"Type": "LIABILITY"}),
    ],
    # Notice: No initial_metrics here. They are generated by the pipeline!
)


# 2. Define Metric Generators (Observers)
class NetWorthGenerator(MetricGenerator):
    def evaluate(self, view):
        assets = sum(
            a.balance for a in view.get_accounts() if a.get_label("Type") == "ASSET"
        )
        liabilities = sum(
            a.balance for a in view.get_accounts() if a.get_label("Type") == "LIABILITY"
        )
        return assets - liabilities


# 3. Define the Computational Pipeline (Mutators)
class JobIncomeFlow(Flow):
    def executeFlow(self, view, updater, logger):
        sam = view.get_person("Sam")
        if not sam:
            logger.error("Person Sam not found in simulation state!")
            return
        if not sam.living():
            logger.info("Person Sam not living.")
        if sam.get_label("Status").current_value() != "Working":
            logger.info("Person Sam not working.")
            return

        updater.emit_transaction(
            Income(
                amount=3000,
                to_account="Joint Checking",
                labels={"IncomeType": "ACTIVE"},
            )
        )


class RetirementCheckFlow(Flow):
    def executeFlow(self, view, updater, logger):
        # Lazily evaluates NetWorthGenerator based on exact account balances RIGHT NOW.
        # This means it accounts for JobIncomeFlow that just ran before it in the pipeline.
        current_net_worth = view.get_metric("Net_Worth")
        if current_net_worth > 1000000:
            logger.info("Net worth target reached! Sam and Alex are now retired.")
            updater.update_person_label("Sam", "Status", "Retired")
            updater.update_person_label("Alex", "Status", "Retired")


# Note: Simulation ends when all people pass their expectancy or max_turns is reached, whichever is first.
pipeline = EngineConfiguration(
    start_date=TurnDate(year=2026, month=2),  # Engine tracks calendar date across turns
    max_turns=TurnDuration(years=60, months=8),
    metrics={"Net_Worth": NetWorthGenerator()},
    flows=[
        JobIncomeFlow(),
        MortgagePaymentFlow(
            from_account="Joint Checking", to_account="Mortgage", amount=1500
        ),
        LivingExpenseFlow(from_account="Joint Checking", amount=2500),
        RetirementCheckFlow(),
    ],
)

# 4. Execute
engine = SimulationEngine(configuration=pipeline)
result = engine.run(scenario)
```

## Specification

> **Design decisions**: see [`docs/adrs/`](./docs/adrs/) for the Architecture Decision Records that explain the key
> tradeoffs behind this design.

### Primary User-Facing Elements

| Element                  | Role                                                                                        |
| ------------------------ | ------------------------------------------------------------------------------------------- |
| `SimulationScenario`     | Defines the **initial state** — persons, accounts, and their labels                         |
| `EngineConfiguration`    | Defines the **computational pipeline** — flows, metric generators, start date, max turns    |
| `SimulationEngine`       | Runs the simulation; call `.run(scenario)` to execute                                       |
| `Flow`                   | User-subclassed component that **mutates** state each turn                                  |
| `MetricGenerator`        | User-subclassed component that **observes** state, returning a numeric or categorical value |
| `SimulationStateView`    | Read-only interface passed to flows and generators                                          |
| `SimulationStateUpdater` | Write interface for emitting transactions and updating labels within a turn                 |
| `SimulationLogger`       | Logging interface for flow-level debug, info, warning, and error messages                   |

### Simulation Lifecycle

```
SimulationScenario   →   EngineConfiguration   →   SimulationEngine.run()
  (initial state)         (pipeline definition)       (produces result)
```

Each turn advances one calendar month. Within a turn:

1. Every `Flow` in `EngineConfiguration.flows` executes in order, mutating state via `SimulationStateUpdater`.
1. `MetricGenerator`s are evaluated **lazily** — only when `view.get_metric()` is called.
1. The completed turn is snapshotted as an immutable `Turn` and appended to the history.

The simulation halts when all persons have passed their life expectancy **or** `max_turns` is reached, whichever comes
first.

### Core Concepts

The architecture is strictly divided into two halves: the **Data Model** (the state of the world) and the
**Computational Model** (the rules that mutate and observe the state).

#### The Data Model

- **Label**: A lightweight tagging system consisting of a Facet and a Value.
- **Person**: Individuals in the simulation, annotated with Labels (e.g., Status: Retired).
- **Account**: A store of monetary value, dynamically opened or closed.
- **Transaction**: Atomic, immutable record of value movement (Income, Expense, Transfer).
- **Metric**: Global numerical or categorical attributes (e.g., Net Worth).
- **Turn**: An immutable snapshot representing a single discrete time step (1 month).
- **SimulationScenario**: The initial starting state of the Data Model before Turn 0 begins.

#### The Computational Model

- **SimulationEngine**: The main controller owning the execution loop.
- **EngineConfiguration**: The pipeline definition, holding Flows, MetricGenerators, etc.
- **Flow**: A computational component injected into the engine at runtime to *mutate* state.
- **MetricGenerator**: A computational component injected to *observe* state, acting as a pure function.
- **SimulationStateView**: Read-only interface for past/current state and lazy Metric evaluation.
- **SimulationStateUpdater**: Controlled write interface for current turn mutation.
- **SimulationLogger**: Interface for Flows to emit debug, warnings, and error messages.
